# ADR-018: §4.4 `context` 확장 - 리뷰 코멘트 객체화, `pr_labels`·`issue_bodies` 추가

- 날짜: **2026-09-23**
- 상태: 채택
- 관련 이슈: #70 (리뷰 코멘트 식별자), #24 (`pr_labels`·`issue_bodies` 추가 여부). 전제: ADR-004(근거 등급 필수), ADR-017(INFERRED 근거 6종 닫힌 목록)
- 결정 경로: CHARTER §4.4 `context` 스키마를 바꾸므로 §13 대상이다. 팀은 정기 회의를 운영하지 않고 비동기로 결정한다. 이 ADR은 희수가 기안하고 PR 리뷰(1명 필수, §8.2)로 팀 확인을 받는다 - 게이트 1 판정(#78) 때와 같은 방식이다

## 맥락

두 이슈가 같은 질문이다. **`pipeline/context.py` 가 이미 수집하고 있는 값 중 무엇을 §4.4 `context` 에 넣을 것인가.** 따로 결정하면 회의를 두 번 하고 ADR 을 두 벌 쓴다.

변경 전 `to_schema_context()` 가 내보내던 것:

```
commit_message · pr_number · pr_title · pr_body · issue_numbers · issue_titles · review_comments
```

`review_comments` 는 **본문 문자열 배열**이었다. 코멘트를 특정할 값이 없다.

수집은 하는데 §4.4 에 칸이 없어 버리던 것: 리뷰 코멘트의 `id`·`path`·`line`·`author`, 그리고 `issue_bodies`·`pr_labels`.

## 결정 1 - 리뷰 코멘트를 객체 배열로 (#70)

```
review_comments:
  - comment_id: int | null
    body: str
    path: str
    line: int | null
    side: enum | null      # LEFT | RIGHT
    outdated: bool
    author: str
```

### 왜

라벨 가이드 §7.2 가 `evidence_locator` 를 `review:comment_1234567` 형식으로 요구한다. 식별자가 없어 **예비 200건에서 17건이 `review:unknown` 또는 공란**으로 남았다.

이것은 형식 문제가 아니다. `evidence_locator` 는 근거 원문을 **다시 찾기 위한** 필드다. 가이드 §8.3 확정 토론에서 두 사람 판정이 갈렸을 때 "네가 본 문장이 어디 있냐" 를 맞춰 볼 수 없으면 불일치 조사가 안 된다. **게이트 1 kappa 가 `reason_label` 0.389 / `evidence_grade` 0.261 이었다.** 500건에서 불일치를 줄이려면 원문 대조가 되어야 하는데, 리뷰 코멘트 근거는 지금 대조가 불가능하다. 예비 200건 리뷰 맥락 결합률이 57.5% 라 500건에서는 더 늘어난다.

### `line` 의 좌표계를 `side` 가 정한다

GitHub 리뷰 코멘트의 `line` 은 어느 파일 기준인지가 `side` 로 갈린다.

- `LEFT` = diff 왼쪽, **부모(삭제 전) 파일**의 줄 번호
- `RIGHT` = diff 오른쪽, **자식(삭제 후) 파일**의 줄 번호

우리 대상은 삭제된 코드라 대부분 `LEFT` 다. `side` 없이 숫자만 두면 어느 파일의 몇 번째 줄인지 알 수 없어 `line` 이 사실상 쓸모가 없다.

### `outdated` 를 따로 두는 이유

코멘트가 달린 뒤 그 자리가 바뀌면 GitHub 은 `line` 을 `null` 로 만들고 `original_line`(코멘트 당시 줄)만 남긴다. 이때 `line` 에 `original_line` 을 채우되 **`outdated` 로 표시한다.**

값을 조용히 바꿔치기하면 과거 좌표를 현재 좌표로 오해한다. 이것은 라벨 가이드 §6.2.3 이 `replacement` 가 `null` 일 때 경고한 것("수집되지 않은 것과 존재하지 않는 것을 구별할 수 없다")과 같은 종류의 함정이다.

줄 정보가 아예 없는 코멘트(`line`·`original_line` 둘 다 없음)는 `outdated` 가 아니다 - "자리가 밀린 것" 이 아니라 애초에 줄에 달리지 않은 것이다.

### 대안

- **형제 배열(`review_comment_ids`)로 id 만 추가** - 기존 필드를 안 건드리지만 두 배열의 순서 맞춤에 기대야 한다. 어긋나면 조용히 틀린 로케이터가 생긴다. #99 에서 `pr_number` 가 화이트리스트에서 빠져 라벨러가 커밋 메시지의 `(#10623)` 을 눈으로 주워 쓴 것과 같은 종류의 함정이다
- **`path`·`line`·`author` 제외하고 `{id, body}` 만** - 이미 수집·필터에 쓰는 값이라 추가 비용이 0이다. "삭제된 그 파일에 달린 코멘트인가" 를 라벨러가 직접 볼 수 있으면 근거 판단이 달라진다

## 결정 2 - `issue_bodies` 추가 (#24)

예비 200건 맥락 결합률은 PR 93.0% / **이슈 36.5%** / 리뷰 57.5% 다. 이슈는 3건 중 1건만 붙는데, 붙은 것에서 **제목만** 보고 있었다. 이유는 제목이 아니라 본문에 적힌다.

가이드 §11-12 가 이미 "보여준다" 로 제안해 두었고 성제가 #7 코멘트에서 제안한 항목이다. 확정만 안 되어 `classify/sampling.py` 에서 `--with-extra-context` 로만 켜지는 상태였다.

### 라이선스 - 데이터셋 공개 때 다시 본다

**이슈 본문은 저장소 라이선스로 덮이지 않는 텍스트다.** 코드가 MIT 라고 해서 이슈 코멘트가 MIT 인 것은 아니다. 지금은 파이프라인 내부에서만 쓰므로 진행하고, **데이터셋 공개(#83 내보내기) 시점에 #28(celery `docs/` CC BY-SA 처리)과 함께 본다.** 여기 기록해 두는 것은 그때 잊지 않기 위해서다.

## 결정 3 - `pr_labels` 는 추가하되 **등급 근거가 아니다** (#24)

`bug`·`performance` 같은 PR 라벨은 이유 8종과 거의 직결되어 분류(§4.2 ③)에 쓸모가 있다. 그래서 `context` 에 넣는다.

**그러나 근거 등급의 근거로는 쓰지 않는다.** 이것은 운영 지침이 아니라 현재 규칙에서 따라 나오는 결론이다.

- **EXPLICIT 이 될 수 없다.** 가이드 §6.1.1 의 E1(이유를 서술하는 문장)·E2(이 삭제에 닿음)를 통과하지 못한다. 라벨은 문장이 아니고, PR 전체에 붙지 이 함수에 붙지 않는다
- **INFERRED 가 될 수 없다.** ADR-017 이 INFERRED 근거를 **닫힌 목록 6종**으로 고정했고 PR 라벨은 그 목록에 없다

**근거로 인정하려면 ADR-017 을 다시 열어야 하고, 그것은 이 ADR 의 범위 밖이다.** `pr_labels` 는 참고 정보다 - 어디를 볼지 좁히는 데 쓰고, 등급은 본문·코드에서 댄다.

## 결과

- `CHARTER.md` §4.4 `context` 갱신 (v1.16)
- `pipeline/context.py` - `ReviewComment` 에 `comment_id`·`side`·`outdated`, `to_schema_context()` 반영
- `classify/sampling.py` 의 `LABELER_CONTEXT_FIELDS` 갱신은 **후속이다.** 라벨러에게 무엇을 보일지는 가이드 §2.1 필드 표가 정하고, 그 표는 성제가 맞춘다. 표가 갱신되면 코드 화이트리스트를 거기 맞춘다
- 가이드 §7.2 의 locator 표기 규칙(`review:comment_<comment_id>`)도 성제가 맞춘다

### 소급하지 않는다

예비 200건의 `review:unknown` 17건은 다시 채우지 않는다. 가이드 §11-16 이 예비 200건을 본 500건에서 제외하기로 했으므로 소급할 이유가 없다.

## 반대 의견 / 미결

- `pr_labels` 를 근거로 쓰고 싶다는 요구가 나오면 ADR-017 재개가 필요하다. 이 ADR 은 그 문을 닫지 않고 **절차를 명시**했다
- 이슈 본문 라이선스는 위 "결정 2" 대로 데이터셋 공개 시점의 미결 항목으로 남는다 (#28 과 함께)
