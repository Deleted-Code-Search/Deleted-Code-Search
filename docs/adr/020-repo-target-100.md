# ADR-020: 저장소 목표 500개 → 100개, 확장 전에 맥락 결합 개선

- 날짜: **2026-10-10**
- 상태: 채택
- 관련 이슈: #128 (확장 계획), #82 (20개 저장소 실행), #166
- 결정 경로: 범위(§3) 변경이므로 §13 대상이다. 조장(성제)이 기안하고 PR 리뷰(1명 필수, §8.2)로 팀 확인을 받는다. 반대 의견은 PR 코멘트로 받는다. **이 결정을 담은 회의록이나 이전 기록은 저장소·이슈에 없다** (2026-10-10 확인: `docs/`, `docs/meetings/`, #128·#82 코멘트). 이 ADR이 첫 기록이다

## 맥락

- CHARTER §3.2 MVP는 "GitHub 상위 저장소 (초기 500개 목표, 실험 후 조정)"였고 §9 4주차에 "저장소 100→500 확장"이 있었다. 500이라는 수는 2026-09-08 v1.0에서 실행 데이터 없이 정한 것이다.
- **교수님 피드백 (2026-09-08, CHARTER §0):** "주제는 매우 좋아 보입니다. 그러나 구현 범위가 너무 넓어 조금 줄이는 것이 좋을 듯 합니다."
- **20개 저장소 실행 실측 (#82, 2026-10-01 완료):**
  - 서버가 없어 팀원 노트북 3대로 나눠 돌렸다 (재헌 6개 · 성제 7개 · 희수 7개, §7).
  - `home-assistant/core` 한 저장소가 `recent_only`(#148) 적용 뒤에도 추출 약 15시간, 맥락 결합 수 시간이었다 (#82 코멘트).
  - 실행 중 저장소 고유의 문제를 고쳐야 했다 — Git 출력 non-UTF-8 디코딩(#144), U+2028에서 JSONL이 잘리는 문제(#146), `recent_only` 구간 반영(#148).
  - 조립 결과는 1,897,048건이다 (규칙 v0.7). 그중 필터 통과(KEPT)는 필터 정밀도 2차 표본의 모집단 기준 465,621건이다 (`docs/reports/filter_precision_v2.md`). §3.2의 "의미 있는 삭제 5만 건 이상"은 20개에서 이미 건수로는 넘는다.
- 게이트 2까지의 사슬(#86 → #87 → #92)은 20개 저장소 기준이다. 확장 계획 이슈 #128은 "#82 실측 처리 시간이 나온 뒤" 착수하기로 돼 있었다.

## 결정

1. **MVP의 저장소 목표를 500개에서 100개로 줄인다.** CHARTER에서 500개로 적힌 곳을 100개로 맞춘다.
2. **100개 확장 전에 맥락 결합 개선을 먼저 한다 (#128).** 순서는 맥락 결합 개선 → 저장소 100개 실행이다. 무엇을 어떻게 고칠지는 #128에서 정한다 — 이 ADR은 순서만 정한다.
3. 확장은 게이트 2 사슬(#86 → #87 → #92)과 **병행**한다. 게이트 2는 20개 저장소의 라벨 500건으로 판정한다.
4. **"의미 있는 삭제 5만 건 이상"(§3.2)은 그대로 둔다.** 20개 저장소의 필터 통과 건수가 이미 그 위다.
5. §3.1 궁극 목표("모든 주요 언어·저장소")와 §11의 "저장소 1,000개로 확대"(의미 있는 삭제가 극히 적을 때의 대응)는 고치지 않는다. 목표가 아니라 방향·비상 대응이다.

## 이유

- **20개에 든 비용으로 500개를 말할 수 없다.** 한 저장소가 추출에만 15시간이 걸린 사례가 있고, 노트북 3대가 전부다. 500개는 20개의 25배다.
- **건수 목표는 이미 넘었다.** 저장소를 늘려서 얻는 것은 건수가 아니라 저장소 다양성이다. 100개면 20개의 5배다.
- **교수님 피드백이 범위 축소였다.** 핵심 4개를 먼저 끝낸다는 ADR-008과 같은 방향이다.
- **같은 맥락 결합을 5배로 돌리기 전에 고친다.** 맥락 결합은 저장소마다 GitHub API를 쓰고 다시 돌리는 비용이 크다. 500건 확정 라벨에서 UNKNOWN이 224건(44.8%)이고 저장소별 회수율(§15 정의 구간)이 8.0%~84.0%로 갈렸다 (`docs/reports/labels_main500.md`). 그 원인 중 맥락 결합으로 고칠 수 있는 것이 있다면 확장 전에 고치는 편이 싸다. **이 숫자의 해석은 아직 정하지 않았다** — 여기서는 순서의 근거로만 쓴다.

## 대안과 버린 이유

- **500개 유지** — 실측 비용으로 볼 때 남은 기간과 노트북 3대로 끝낼 수 있다고 말할 근거가 없다.
- **20개에서 멈춤** — 저장소 20개는 선정 기준(§4.3)을 통과한 것 중 일부다. 필터 정밀도·분류기 성능이 저장소 구성에 얼마나 기대는지 볼 수 없다 (#128 "재확인 항목").
- **맥락 결합 개선 없이 바로 100개 실행** — 개선이 뒤에 오면 100개를 다시 돌려야 한다.
- **확장을 게이트 2 뒤로** — 게이트 2 사슬은 희수·성제 쪽 일이고 확장은 파이프라인 쪽 일이라 병행할 수 있다.

## 영향

- CHARTER.md: §2.2·§2.3 표·§3.2·§4.3·§7 용량 추정·§9 4주차 행·§10.5·§12.2·§12.3의 500개 → 100개, §5 표에 ADR-020 행, §19 기록 (v1.19).
- **이슈 #128의 제목·본문은 아직 "20개 → 500개"다.** 이 ADR에 맞춰 고치고, 맥락 결합 개선의 범위를 거기서 정한다. #25(저장소 유형 필터, "500개 확장 대비")도 같다.
- 100개로 늘리면 저장소 구성이 바뀐다. 필터 정밀도(§10.1)와 분류기 성능(§10.2)이 20개에서 잰 값 그대로인지는 다시 봐야 한다 (#128). 저장소 선정 기준(§4.3, ADR-006 미갱신)도 100개를 고르기 전에 정리한다.
- 스키마·분류 체계·라벨 데이터는 바뀌지 않는다.
