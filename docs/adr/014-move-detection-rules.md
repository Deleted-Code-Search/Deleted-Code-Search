# ADR-014: 이동 탐지 세부 규칙 — 정규화·유사도·후보 범위

- 날짜: **2026-09-15**
- 상태: 채택
- 관련 이슈: #53 (이 ADR), #52 (구현, 재헌)
- 결정 경로: 조장(성제) 결정 → 이 ADR을 담은 PR의 리뷰(1명 필수, §8.2)로 팀 확인. 별도 회의록은 없다

## 맥락
- CHARTER.md §4.2 ②는 이동을 "같은 커밋에서 정규화 본문 유사도 ≥ 0.9인 함수가 다른 파일/위치에 추가됨"으로 정의한다.
  **정규화 방법, 유사도 계산 방식, 추가 함수 후보 범위는 정해져 있지 않다.**
- #52(이동 탐지 필터 구현, 재헌) 진행 중 이 세 가지에 대한 확인 요청이 들어왔고, 조장이 결정했다.
- 2026-09-14 사전 탐색(`docs/evaluation.md`, #47)에서 필터 미적용 상태의 `psf/requests` **최근 300커밋** FULL_FUNCTION 242건 중
  235건(97.1%)이 커밋 d63e94f "Move to src directory (#6506)" 하나에서 나왔다. 전체 히스토리 기준으로는 3,007건 중 235건이다.
- 필터 규칙 버전 변경은 §13 변경 절차 대상이다.

## 결정 1 — 정규화는 AST(tree-sitter) 기반

치환한다:
- 식별자(변수명·파라미터명) → `VAR`
- 다른 함수의 본문에 포함된 **중첩 함수 선언의 이름** → `VAR`
- 문자열 리터럴 → `STR`, 숫자 리터럴 → `NUM`
- 주석·독스트링은 제거하고, 공백·들여쓰기는 정규화한다

치환하지 않는다:
- **현재 비교 대상 함수의 이름** (`Function.name`)
- 속성 접근과 호출 대상 이름 (`self.headers`, `json.loads` 등)

**중첩 함수 이름의 범위.** `PythonAdapter`는 중첩 함수를 바깥 함수와 별도의 `Function`으로도 추출한다. 같은 이름을 자리에 따라 다르게 다룬다.
- 바깥 함수를 비교할 때: 그 본문 안에 있는 중첩 함수 선언의 이름은 `VAR`로 치환한다
- 별도로 추출된 중첩 함수를 비교할 때: 자신의 이름을 대상 함수 이름으로 취급해 보존한다

**이유.** 함수명을 치환하면 이동과 리네임(본문 동일·이름만 변경, §4.2 ②의 별도 노이즈 유형)이 구분되지 않는다.
속성·호출 이름을 치환하면 전혀 다른 함수가 같아 보인다. 이 단계의 목적은 "같은 코드를 옮긴 것"을 잡는 것이지
"비슷한 코드"를 찾는 것이 아니므로, 치환은 적을수록 안전하다.

이 규칙은 §4.2 파서 계층의 "정규화 본문"과 §4.4 `deleted_body_normalized`("변수명·리터럴 치환")를 구체화한다. 필드 자체는 바꾸지 않는다.

## 결정 2 — 유사도는 2단계

1. 정규화 본문이 **완전히 같으면** 이동으로 확정한다.
2. 아니면 `difflib.SequenceMatcher.ratio()`가 **0.9 이상**(0.9 포함)이면 이동으로 판정한다.

**이유.** 파일 이동은 본문을 그대로 옮기므로 대부분 1단계에서 걸릴 것으로 본다. 사전 탐색에서 최근 300커밋 FULL_FUNCTION의
97.1%가 파일 이동 커밋 하나였다. 다만 **1단계에서 실제로 몇 %가 걸리는지는 아직 재지 않았다.** #52 구현 후 확인한다.
`difflib`는 표준 라이브러리라 새 의존성이 없다. 이 단계는 확실한 노이즈를 걷어내는 것이 목적이라 정교함보다 안정성이 우선이다.

**계산 조건 (명세 보완 — 결정 3의 1차 거르기가 성립하려면 필요하다):**
- 비교 단위는 정규화 본문의 **줄 목록**이다: `SequenceMatcher(None, 삭제_줄목록, 추가_줄목록, autojunk=False)`
- `autojunk=False`: 기본값은 원소가 200개 이상인 시퀀스에서 자주 나오는 줄을 무시해, 긴 함수의 비율을 실제보다 낮게 낸다
- 인자 순서는 (삭제 함수, 추가 함수)로 고정한다. `ratio()`는 인자 순서에 따라 값이 달라질 수 있다

## 결정 3 — 후보 범위는 같은 커밋에서 경로 또는 위치가 다른 추가 함수

- 같은 커밋에서 추가된 함수 가운데 **파일 경로 또는 위치가 삭제 함수와 다른 것만** 후보로 본다. 다른 파일에 추가된 함수와 같은 파일 안에서 위치가 바뀐 함수가 여기에 해당한다.
- **같은 경로·같은 위치**의 추가 함수는 유사도 계산 전에 후보에서 제외하고 **수정**으로 처리한다 (NOISE_MOVE로 판정하지 않는다).
  - "같은 위치"의 판정 기준(부모 커밋 줄 번호와 자식 커밋 줄 번호의 대응 방식)은 이 ADR에서 정하지 않는다. #52 구현에서 정하고 `docs/filter_rules.md`에 반영한다.
- **정규화 본문이 0줄인 함수는 이동 후보에서 제외한다.** 삭제 함수가 0줄이면 0줄이 아닌 후보와는 아래 1차 거르기에서 걸러지므로, 0줄 삭제 함수는 NOISE_MOVE로 판정되지 않는다.
- 비교 전 1차 거르기: **줄 수 차이가 20%를 넘으면 비교하지 않는다.** 유사도 0.9를 넘을 수 없기 때문이다.

**1차 거르기의 정의 (명세 보완):**
- 줄 수는 **정규화 본문**의 줄 수다.
- 차이는 **긴 쪽 기준**으로 잰다: `(긴 쪽 줄 수 − 짧은 쪽 줄 수) / 긴 쪽 줄 수 > 0.2`이면 비교하지 않는다.
- 근거: `ratio() = 2M / (a + b)`이고 일치 원소 수 `M ≤ 짧은 쪽`이다. 차이가 긴 쪽의 20%를 넘으면 상한이 `2 × 0.8 / 1.8 ≈ 0.889 < 0.9`다.
  짧은 쪽 기준으로 재면 상한이 `2 / 2.2 ≈ 0.909`가 되어, 0.9를 넘는 쌍을 걸러 버릴 수 있다.
- 1단계(완전 일치)는 줄 수가 같으므로 이 거르기의 영향을 받지 않는다.
- 0줄 본문은 위 규칙으로 먼저 제외하므로 이 식의 분모(긴 쪽 줄 수)는 0이 되지 않는다.

**이유.** "삭제 위치와 겹치는 추가 함수만" 보면 파일 이동을 잡을 수 없다. 이동은 정의상 다른 경로로 가는 것이다.
줄 수 1차 거르기가 없으면 삭제 N개 × 추가 M개 비교가 대량 커밋에서 폭증한다.

**이유 — 같은 경로·같은 위치 제외.** CHARTER §4.2 ②의 이동 정의가 "다른 파일/**위치**에 추가됨"이다.
제자리 수정을 후보에 넣으면 아래 "한계"의 사례(줄 수의 10% 이하만 바꾼 수정, 식별자·리터럴만 바꾼 수정)가 NOISE_MOVE로 걸러져
**실제 삭제 데이터가 유실된다.** 같은 파일 안에서 위치만 바뀌는 이동은 위치가 다르므로 후보에 남는다.

**이유 — 0줄 본문 제외.** 0줄이면 1차 거르기의 분모가 0이 된다. 또 빈 본문끼리의 완전 일치를 이동으로 보면
독스트링만 있는 서로 다른 함수가 전부 같아진다.
참고로 `Function.body`는 데코레이터·시그니처를 포함하고(`pipeline/parsers/base.py`) 결정 1은 대상 함수 이름을 보존한다.
그래서 시그니처 줄을 정규화 본문에 남기는 구현에서는 0줄이 생기지 않는다. 이 규칙은 정규화가 시그니처를 떼는 구현까지 막는 방어 규칙이다.

**한계 — 임계값이 가르지 못하는 수정 (`difflib`로 계산, 줄 목록 기준).** 임계값이 수정과 이동을 가르는 것은 수정 폭이 줄 수의 10%를 넘을 때다.
이 사례를 제자리 수정에서 막으려고 같은 경로·같은 위치를 후보에서 뺐다. **위치를 옮기면서 조금 고친 함수는 여전히 이동으로 판정된다.**

| 수정 | ratio | 판정 |
|---|---:|---|
| 10줄 중 1줄 | 0.900 | 이동 |
| 20줄 중 1줄 | 0.950 | 이동 |
| 30줄 중 3줄 | 0.900 | 이동 |
| 10줄 중 2줄 | 0.800 | 이동 아님 |

- 결정 1의 정규화는 식별자·리터럴을 치환하므로, 위치를 옮기면서 식별자나 리터럴만 바꾼 함수는 정규화 본문이 완전히 같아져 1단계에서 이동으로 판정된다. 제자리에서 바꾼 경우는 후보에서 빠지므로 해당하지 않는다.
- PARTIAL 레코드(함수 일부만 삭제된 수정)는 대개 제자리 수정이라 같은 경로·같은 위치 규칙으로 후보에서 빠진다. PARTIAL에 이동 필터를 적용할지 자체는 이 ADR에서 정하지 않았다.
- 이런 경우가 실제 데이터에 얼마나 있는지는 #52 구현 후 정밀도 재측정(§10.1)에서 확인한다.

## 대안과 버린 이유
- **토큰 기반 유사도** (결정 2) — 정확도는 높지만 이 용도에서 얻는 것이 적다. 이 단계는 같은 코드를 옮긴 것을 잡는 확실한 노이즈 제거다.
- **삭제 위치와 겹치는 추가 함수만 후보로** (결정 3) — 파일 이동을 잡을 수 없다.
- **같은 파일의 추가 함수를 모두 후보로** (결정 3, PR #54 두 번째 커밋에서 한때 채택) — 제자리 수정 중 줄 수의 10% 이하만 바꾼 수정과 식별자·리터럴만 바꾼 수정이 NOISE_MOVE로 걸러져 실제 삭제 데이터가 유실된다. PR #54 리뷰(CodeRabbit) 지적으로 같은 경로·같은 위치를 제외하도록 바꿨다.

## 영향
- `pipeline/filter.py` 구현: #52 (재헌).
- 후속 구현에는 **추가 함수의 파일 경로와 위치 메타데이터**(자식 커밋 기준 시작·끝 줄)가 필요하다. 현재 `pipeline/extract.py`는 삭제 쪽(부모 커밋) 함수만 추출하므로, 추가 쪽 함수 정보를 내부적으로 확보하도록 확장해야 한다. **JSONL 스키마와 공개 인터페이스는 바꾸지 않는 방향**이다. 이 PR에서는 코드를 바꾸지 않는다.
- 임계값 0.9는 §4.2 ②에 이미 있으므로 이 ADR에서 바꾸지 않는다.
- 필터 규칙 버전이 올라가므로 §4.2 ②에 따라 **정밀도를 재측정**해야 한다. 목표는 §10.1 기준 정밀도 ≥ 90%, kappa ≥ 0.7이다.
  §9 3주차 확인 지점에 "≥ 85%"로 적혀 있던 값은 평가 계획 본문(§10.1)에 맞춰 90%로 통일했다 (CHARTER v1.10).
- **#52 본문과의 관계:** 완료 조건 "같은 경로 내 수정/삭제를 이동으로 오인하지 않음"은 결정 3과 맞는다. 판정 기준
  "삭제된 함수와 다른 경로에 추가된 함수를 비교"는 같은 파일 안의 위치 이동까지 넓혀야 한다.
  #52 코멘트를 이 내용으로 고쳤다. 이전 판에 적은 "같은 파일의 추가 함수 전부 포함, 수정은 임계값으로 가른다"는 틀려서 정정했다.
- `docs/filter_rules.md` NOISE_MOVE 규칙에 반영했다 (v0.1). **이 문서화 PR은 규칙 명세와 버전 표기만 한다.** 테스트, `DeletionRecord.filter_rule_version` 반영, 수동 100건 정밀도 재측정은 #52 구현 PR에서 한다.
- CHARTER.md §5 표에 행 추가(v1.9), §9 3주차 필터 정밀도 목표를 90%로 통일(v1.10), 결정 3 수정 반영(v1.11), §19 기록.
- 스키마·분류 체계·파서 인터페이스 변경 없음. 라벨 데이터가 없어 재라벨 비용도 없다.
