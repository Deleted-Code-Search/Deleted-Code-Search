# ADR-014: 이동 탐지 세부 규칙 — 정규화·유사도·후보 범위

- 날짜: **2026-09-15**
- 상태: 채택
- 관련 이슈: #53 (이 ADR), #52 (구현, 재헌)
- 결정 경로: 조장(성제) 결정 → 이 ADR을 담은 PR의 리뷰(1명 필수, §8.2)로 팀 확인. 별도 회의록은 없다

## 맥락
- CHARTER.md §4.2 ②는 이동을 "같은 커밋에서 정규화 본문 유사도 ≥ 0.9인 함수가 다른 파일/위치에 추가됨"으로 정의한다.
  **정규화 방법, 유사도 계산 방식, 추가 함수 후보 범위는 정해져 있지 않다.**
- #52(이동 탐지 필터 구현, 재헌) 진행 중 이 세 가지에 대한 확인 요청이 들어왔고, 조장이 결정했다.
- 2026-09-14 사전 탐색(`docs/evaluation.md`, #47)에서 필터 미적용 상태의 `psf/requests` **최근 300커밋** FULL_FUNCTION 242건 중
  235건(97.1%)이 커밋 d63e94f "Move to src directory (#6506)" 하나에서 나왔다. 전체 히스토리 기준으로는 3,007건 중 235건이다.
- 필터 규칙 버전 변경은 §13 변경 절차 대상이다.

## 결정 1 — 정규화는 AST(tree-sitter) 기반

치환한다:
- 식별자(변수명·파라미터명·지역 함수명) → `VAR`
- 문자열 리터럴 → `STR`, 숫자 리터럴 → `NUM`
- 주석·독스트링은 제거하고, 공백·들여쓰기는 정규화한다

치환하지 않는다:
- 함수명 자체
- 속성 접근과 호출 대상 이름 (`self.headers`, `json.loads` 등)

**이유.** 함수명을 치환하면 이동과 리네임(본문 동일·이름만 변경, §4.2 ②의 별도 노이즈 유형)이 구분되지 않는다.
속성·호출 이름을 치환하면 전혀 다른 함수가 같아 보인다. 이 단계의 목적은 "같은 코드를 옮긴 것"을 잡는 것이지
"비슷한 코드"를 찾는 것이 아니므로, 치환은 적을수록 안전하다.

이 규칙은 §4.2 파서 계층의 "정규화 본문"과 §4.4 `deleted_body_normalized`("변수명·리터럴 치환")를 구체화한다. 필드 자체는 바꾸지 않는다.

## 결정 2 — 유사도는 2단계

1. 정규화 본문이 **완전히 같으면** 이동으로 확정한다.
2. 아니면 `difflib.SequenceMatcher.ratio()`가 **0.9 이상**(0.9 포함)이면 이동으로 판정한다.

**이유.** 파일 이동은 본문을 그대로 옮기므로 대부분 1단계에서 걸릴 것으로 본다. 사전 탐색에서 최근 300커밋 FULL_FUNCTION의
97.1%가 파일 이동 커밋 하나였다. 다만 **1단계에서 실제로 몇 %가 걸리는지는 아직 재지 않았다.** #52 구현 후 확인한다.
`difflib`는 표준 라이브러리라 새 의존성이 없다. 이 단계는 확실한 노이즈를 걷어내는 것이 목적이라 정교함보다 안정성이 우선이다.

**계산 조건 (명세 보완 — 결정 3의 1차 거르기가 성립하려면 필요하다):**
- 비교 단위는 정규화 본문의 **줄 목록**이다: `SequenceMatcher(None, 삭제_줄목록, 추가_줄목록, autojunk=False)`
- `autojunk=False`: 기본값은 원소가 200개 이상인 시퀀스에서 자주 나오는 줄을 무시해, 긴 함수의 비율을 실제보다 낮게 낸다
- 인자 순서는 (삭제 함수, 추가 함수)로 고정한다. `ratio()`는 인자 순서에 따라 값이 달라질 수 있다

## 결정 3 — 후보 범위는 같은 커밋의 모든 추가 함수

- 같은 커밋에서 추가된 **모든** 함수를 후보로 본다. 다른 파일에 추가된 함수도 포함한다.
- **같은 파일에 추가된 함수도 후보에 포함한다.**
- 비교 전 1차 거르기: **줄 수 차이가 20%를 넘으면 비교하지 않는다.** 유사도 0.9를 넘을 수 없기 때문이다.

**1차 거르기의 정의 (명세 보완):**
- 줄 수는 **정규화 본문**의 줄 수다.
- 차이는 **긴 쪽 기준**으로 잰다: `(긴 쪽 줄 수 − 짧은 쪽 줄 수) / 긴 쪽 줄 수 > 0.2`이면 비교하지 않는다.
- 근거: `ratio() = 2M / (a + b)`이고 일치 원소 수 `M ≤ 짧은 쪽`이다. 차이가 긴 쪽의 20%를 넘으면 상한이 `2 × 0.8 / 1.8 ≈ 0.889 < 0.9`다.
  짧은 쪽 기준으로 재면 상한이 `2 / 2.2 ≈ 0.909`가 되어, 0.9를 넘는 쌍을 걸러 버릴 수 있다.
- 1단계(완전 일치)는 줄 수가 같으므로 이 거르기의 영향을 받지 않는다.

**이유.** "삭제 위치와 겹치는 추가 함수만" 보면 파일 이동을 잡을 수 없다. 이동은 정의상 다른 경로로 가는 것이다.
줄 수 1차 거르기가 없으면 삭제 N개 × 추가 M개 비교가 대량 커밋에서 폭증한다.

**이유 — 같은 파일 포함.** CHARTER §4.2 ②는 이동을 "다른 파일/**위치**에 추가됨"으로 정의한다.
같은 파일 안에서 위치만 바뀌는 이동도 이동이다. 같은 경로의 수정을 이동으로 오인하는 문제는 유사도 0.9 임계값이 막는다.
함수를 수정하면 정규화 본문 유사도가 떨어진다. **후보 범위를 좁혀서 해결할 문제가 아니다.**

**한계 — 임계값이 막지 못하는 수정 (`difflib`로 계산, 줄 목록 기준).** 임계값이 막는 것은 수정 폭이 줄 수의 10%를 넘을 때다.

| 수정 | ratio | 판정 |
|---|---:|---|
| 10줄 중 1줄 | 0.900 | 이동 |
| 20줄 중 1줄 | 0.950 | 이동 |
| 30줄 중 3줄 | 0.900 | 이동 |
| 10줄 중 2줄 | 0.800 | 이동 아님 |

- 결정 1의 정규화는 식별자·리터럴을 치환하므로, 식별자나 리터럴만 바꾼 수정은 정규화 본문이 완전히 같아져 1단계에서 이동으로 판정된다.
- PARTIAL 레코드(함수 일부만 삭제된 수정)에 이 필터를 적용할지는 이 ADR에서 정하지 않았다. 적용하면 위 한계가 작은 수정에 직접 걸린다.
- 이런 경우가 실제 데이터에 얼마나 있는지는 #52 구현 후 정밀도 재측정(§10.1)에서 확인한다.

## 대안과 버린 이유
- **토큰 기반 유사도** (결정 2) — 정확도는 높지만 이 용도에서 얻는 것이 적다. 이 단계는 같은 코드를 옮긴 것을 잡는 확실한 노이즈 제거다.
- **삭제 위치와 겹치는 추가 함수만 후보로** (결정 3) — 파일 이동을 잡을 수 없다.

## 영향
- `pipeline/filter.py` 구현: #52 (재헌).
- `pipeline/extract.py`가 추가 쪽(added-side)의 경로·함수 정보를 내부적으로 확보하도록 확장이 필요하다. **JSONL 스키마와 공개 인터페이스는 바꾸지 않는 방향**이다.
- 임계값 0.9는 §4.2 ②에 이미 있으므로 이 ADR에서 바꾸지 않는다.
- 필터 규칙 버전이 올라가므로 §4.2 ②에 따라 **정밀도를 재측정**해야 한다. 목표는 §10.1 기준 정밀도 ≥ 90%, kappa ≥ 0.7이다.
  §9 3주차 확인 지점에 "≥ 85%"로 적혀 있던 값은 평가 계획 본문(§10.1)에 맞춰 90%로 통일했다 (CHARTER v1.10).
- **#52 본문과 다르다:** #52는 판정 기준을 "삭제된 함수와 다른 경로에 추가된 함수를 비교"로, 완료 조건에
  "같은 경로 내 수정/삭제를 이동으로 오인하지 않음"을 두었다. 결정 3은 같은 파일의 추가 함수도 후보에 넣는다.
  이 결정과 위 한계를 #52에 코멘트로 알렸다. 같은 경로 수정의 오인은 후보 범위가 아니라 임계값과 테스트로 다룬다.
- `docs/filter_rules.md` NOISE_MOVE 규칙에 반영했다 (v0.1, 구현 전).
- CHARTER.md §5 표에 행 추가(v1.9), §9 3주차 필터 정밀도 목표를 90%로 통일(v1.10), §19 기록.
- 스키마·분류 체계·파서 인터페이스 변경 없음. 라벨 데이터가 없어 재라벨 비용도 없다.
