## 시도했다가 버린 것 / 발견 → 원인 → 조치 (§8.7 실패 기록 원칙)

**1. 필터 정밀도 1차 측정 — 결과는 남기고, 그 방식은 버렸다**
- 시도: 사전 등록대로 KEPT 100 + NOISE_MOVE 50 + NOISE_TRIVIAL 50을 3인이 독립 판정했다
- 결과: 정밀도 57.0%(목표 90%), Fleiss kappa 0.462(목표 0.7). 둘 다 미달
- 왜 그 방식으로는 안 됐나 (PR #151 분석):
  - **판정 화면에 추가된 코드가 없었다.** 판정자가 diff를 보지 못하고 커밋 메시지로 추정했다 (`note`에 "not verified in diff"가 sj 139건, hs 65건). 같은 로직이 다른 모양으로 다시 나타나는 제자리 재작성을 한 사람은 "아니오", 다른 사람은 "예"로 봤다 — 불일치 70건 중 49건이 이 패턴이다
  - **사전 등록한 "미달 시" 절차가 원인과 맞지 않았다.** #80에서 보류한 항목(이동+리네임 0.9 미만, 커밋 간 이동)으로 고쳐지는 건이 KEPT "아니오" 43건 중 0건이었다. 가장 큰 원인은 포맷 변경 17건이었고 그것은 CHARTER §4.2 ②에 있으나 구현하지 않은 `NOISE_FORMAT`이다
  - 사후 적용 가능한 규칙을 다 넣어도 표본 안에서 68.7%였다
- 버린 것: 1차의 판정 기준 문구, 추가 코드 없는 판정 화면, #80 보류 항목 재검토 절차
- 대안: 2차 재측정을 새로 사전 등록했다 — 판정 기준을 §6.3.3 1~5번으로, 화면에 추가 헝크를, 필터에 `NOISE_FORMAT`을 넣고 **새 시드로 새 표본**을 뽑는다. 1차 결과 숫자와 사전 등록 문서는 고치지 않고 그대로 뒀다

**2. JSONL을 `splitlines()`로 읽으면 레코드가 잘린다**
- 발견: #82 실행 중 langchain 맥락 결합이 멈췄다 (#146)
- 원인: `json.dumps(ensure_ascii=False)`는 U+2028을 이스케이프하지 않는데 `str.splitlines()`는 그것을 줄바꿈으로 본다. 커밋 메시지에 그 문자가 실제로 있었다
- 조치: 파일을 줄 단위로 순회해 읽는다 (PR #147). 같은 문제가 추출 쪽에도 있는지는 #82 완료 코멘트에 "확인 결과에 따라 해당 저장소만 재추출"로 남아 있다

## 안 된 것과 이유
- **필터 정밀도 90% 미달** (57.0%). 위 1번
- **필터 판정자 간 kappa 미달** (0.462). 판정 기준이 사람마다 다르게 읽혔다
- **500건 라벨링은 이 주에 시작하지 못했다.** 입력(표본·화면·병합 도구)이 이 주 후반에야 갖춰졌다

## 배운 것
**사전 등록은 "미달 시 무엇을 한다"까지 맞혀 주지 않는다.** 1차 사전 등록은 미달 시 #80 보류 항목을 재검토한다고 적었는데, 실제 원인은 거기 없었다. 그래도 사전 등록이 있었기 때문에 "기준을 결과에 맞췄다"가 되지 않고, 1차 결과를 그대로 둔 채 2차를 새 표본으로 다시 잴 수 있었다.
**판정자에게 판정에 필요한 것이 화면에 있는지를 먼저 본다.** kappa가 낮았던 원인의 큰 부분이 규칙이 아니라 화면이었다. 같은 문제가 라벨 화면에도 있어 #155에서 둘을 함께 고쳤다.
