## 1. 읽는 법

- **가장 큰 변화는 모델 교체다.** 같은 c4 에서 flash lenient 78.0% · strict 60.0% → nemotron lenient 80.0% · strict 70.0% (둘 다 LLM 단독)
- **큰 모델에서는 scikit-learn 모델을 더하면 오히려 내려간다.** s3 모델+LLM lenient 77.0% · strict 65.0%. `WEIGHT_LLM` 0.5 는 flash 답에 맞춰 고른 값이다. LLM 단독 설정은 `r1+m2+c3` 와 다른 구성이라는 뜻이기도 하다
- **few-shot 은 올리지 못했다.** flash s2 lenient 75.0% · strict 60.0%, nemotron s5 lenient 74.0% · strict 61.0%. 둘 다 같은 모델의 c4 보다 낮다
- **UNK 판단 기준(c4)만으로는 거의 안 움직였다.** s1 lenient 78.0% · strict 61.0% (게이트 2 lenient 78.0% · strict 60.0%)
- **API 없는 섞기는 lenient 를 못 올렸다.** 최고 `massage/blend:design-b확인` lenient 78.0% · strict 63.0%. 기준선 B 를 믿고 UNK 를 뒤집으면 크게 떨어진다
- **`massage/s4` 은 결과가 아니다.** mistralai/mistral-large-4-1t-a52b 호출 24건이 모두 300초 시간 초과라 30분 규칙으로 멈췄다. 표의 lenient 72.0% · strict 55.0% 는 LLM 없이 모델만 낸 값이고 순위에 넣지 않았다
- **차이가 작다.** 100건이라 구간이 ±8%p 안팎이고 lenient 바닥(전부 UNK)도 67.0% 다. 온도 0.7 답이 섞인 s6·다수결의 1~3%p 차이는 우연과 구별되지 않는다
- 최고 설정의 UNK 혼동: 정답 UNK / 예측 UNK 42건, 정답 UNK / 예측 이유 8건, 정답 이유 / 예측 UNK 10건, 정답 이유 / 예측 이유 40건

## 5. 프롬프트·모델 고른 기록

- **유료 API 는 부르지 않았다.** 호출기는 NVIDIA URL 과 허용 목록의 세 모델만 부르고, 다른 공급자 키는 프로세스에서 지운다 (`eval/massage_stage2.py`, 테스트 있음)
- **c4** = c3 + 라벨링 가이드 §5·§6.2.1·§6.3.1 의 UNK 판단 기준. **c5** = c4 + train 예시 10건
- few-shot 은 train 에서 라벨러 둘이 일치한 건만, val·test 와 같은 커밋을 빼고, 칸(라벨, 테스트 여부)마다 짧은 순으로 기계적으로 골랐다. UNK 4 · DESIGN 2 · DEAD 2 · FEAT 1 · LIB 1
- 모델: `nvidia/nemotron-3-ultra-550b-a55b`(550B) 와 `mistralai/mistral-large-4-1t-a52b`(1T). 2026-11-03 목록(85개)과 모델 쪽 "Free Endpoint" 표시, 짧은 호출로 확인했다. 답이 오지 않는 후보 `moonshotai/kimi-k2.6`(404) 은 뺐다
- 설정 순서는 s1·s2 를 본 뒤 c4 를 골랐고, s3 을 본 뒤 s5·s6 을 nemotron 으로 정했다. 즉 test 결과가 다음 설정을 정했다
- 큰 모델은 생각 과정을 끄지 못해 토큰 상한을 4096 으로 올렸다 (flash 는 256 그대로)
- s6 은 온도 0.7 로 3번 물었다. 온도 0 이면 같은 답이 나와 다수결이 뜻이 없다. 셋 다 갈리면 UNK 로 본다. 무료 한도(429)로 세 번 이어 돌려 100건 모두 3표를 채웠다
- 호출 실패는 다음 차례에 다시 묻고, 끝내 답이 없으면 게이트 2 와 같이 LLM 표 없이 낸다. 시간 초과는 300초 그대로다
- 프롬프트·설정은 이 모듈에만 있다. `classify/` 와 main·기존 보고서·dataset-v0.9 는 바꾸지 않았다
