# 저장소 100개 선정 (초안)

ADR-020(저장소 목표 500 → 100)의 100개 목록 초안이다. 확정 20개(`repo_final20.md`)는 그대로 두고 80개를 더했다.
지표 정의는 `repo_selection.md`, 선정 기준 v2는 `evaluation.md` "2026-09-15 — 저장소 선정 기준 v2" 절에 있다.

- 산출일: 2026-10-13 / 이슈 #171 / ADR-020
- **상태: 초안. 팀 확인 전이다.** 사람이 정해야 하는 것은 §8·§9에 모았다
- 선정 기준은 바꾸지 않았다. 바꾸는 편이 낫다고 본 것은 §8에 **변경 제안**으로만 적었다
- 파이프라인은 돌리지 않았다. 기존 20개의 구성과 `repo_final20.md`·`repo_final20_v2.csv`는 건드리지 않았다
- 파일

| 파일 | 내용 |
|---|---|
| `docs/repo_final100.csv` | 100개 전체 목록. `repo_final20_v2.csv`와 같은 열 (`select_repos.py` v2 출력 그대로). **실행 입력으로 쓰지 않는다** |
| `docs/repo_final100_sj.csv` · `_jh.csv` · `_hs.csv` | **파이프라인 실행 입력.** 담당별 신규 저장소만 (합쳐서 80개, 위와 같은 열). 분할은 §7.2 |
| `docs/repo_candidates_100.csv` | 1단계 원본. 검색 500개 + §4.3 예시의 v1 평가 (502행, 제외 사유 포함) |
| `docs/repo_candidates_100_v2.csv` | 2단계 원본. PR 게이트 통과 155개 + celery의 v2 평가 |
| `docs/repo_final100_scale.csv` | 100개의 예상 규모·API 부담 어림 (`tools/repo_scale.py` 출력) |

> **실행할 때: 기존 20개는 다시 돌리지 않는다. `pipeline.run`의 입력은 담당별 CSV(`repo_final100_sj.csv` · `_jh.csv` · `_hs.csv`)다.**
> `repo_final100.csv`를 그대로 넣으면 기존 20개가 다시 추출된다 (실행 기록이 필터 v0.7, 지금은 v0.8 — home-assistant만 약 15시간). 이유와 절차는 §7.

## 0. 요약

- **100개 = 기존 20 + 신규 80.** 신규 80은 PR 게이트를 통과한 후보 중 `score_v2` 상위 80개다
- 라이선스: Apache-2.0 51 / MIT 39 / BSD-3-Clause 9 / BSD-2-Clause 1. 수동 확인은 celery 하나뿐이다 (기존 그대로)
- `recent_only`(최초 커밋 2015년 이전, 채굴 구간을 2015년부터로 좁힘) 19개, 2015년 이후 시작 81개, 그중 2020년 이후 시작 52개
- 신규 80개의 예상 규모 (**어림**, §5): 클론 합계 약 34.5GB, 순회 커밋 약 608,203개, 추출 시간 32시간~111시간 (노트북 1대 직렬 환산, 중간값 63시간)
- 신규 80개의 맥락 결합 API 호출 (**어림**, §6): 46,268~182,183회, 중간값 108,443회. 토큰 하나(5,000회/시간)로 21.7시간, 셋으로 나누면 한 사람당 7.2시간 안팎이다
- 초대형(XL) 신규 2개: `zulip/zulip`, `roboflow/supervision`. `ccxt/ccxt`(단독 클론 약 10.7GB)는 팀 결정으로 뺐다 (§1.4)
- 3분할 초안은 §7에 있다

## 1. 방법

### 1.1 흐름

20개를 고를 때(`repo_final20.md`)와 같은 스크립트·같은 순서다. 달라진 것은 검색 범위(100 → 500개)와 PR 게이트를 컷으로 쓴 것뿐이다.

1. **1단계 (v1).** 검색 `language:Python is:public archived:false stars:>=1000` 별 수 내림차순 500개 + §4.3 초기 후보 예시를 `select_repos.py`로 평가했다. 언어·라이선스·커밋 수·최근 1년 활동으로 거르고, 남은 저장소마다 최근 1년 커밋 표본 30건(병합·봇 제외)에서 `pr_ratio`·`issue_ref_ratio`를 쟀다
2. **PR 게이트.** `pr_ratio ≥ 0.70`인 후보만 다음 단계로 넘겼다
3. **2단계 (v2).** 게이트 통과 후보와 celery를 `--history-per-year 5`로 다시 평가했다. 최초 커밋 날짜, `recent_only`, 연도별 PR 연결 비율, `score_v2`가 여기서 나온다
4. **선례 적용.** `repo_final20.md` §2에서 사람이 뺀 두 부류(신생, 예제·목록 모음)를 같은 이유로 뺐다. 여기에 팀 결정으로 `ccxt/ccxt`를 더 뺐다 (§1.4)
5. **확정 20개는 그대로 넣고, 나머지를 `score_v2` 내림차순으로 80개 채웠다**

별 수는 검색 범위를 정하는 데만 썼다 (ADR-006). 순위에는 들어가지 않는다.

### 1.2 재현

```bash
# 1단계
python -m pipeline.select_repos --max-candidates 500 --commit-sample 30 --out docs/repo_candidates_100.csv

# 2단계: 1단계 CSV에서 selection_status=CANDIDATE 이고 pr_gate_pass=true 인 저장소 + celery/celery
python -m pipeline.select_repos --repos <위 목록> --history-per-year 5 \
  --license-override celery/celery=BSD-3-Clause --out docs/repo_candidates_100_v2.csv

# 확정 100개 (2단계 캐시를 그대로 읽으므로 API 호출 0회, 행 내용은 2단계 CSV와 같다)
python -m pipeline.select_repos --repos <100개> --history-per-year 5 \
  --license-override celery/celery=BSD-3-Clause --out docs/repo_final100.csv

# 예상 규모·API 부담 어림
python -m tools.repo_scale --input docs/repo_final100.csv --out docs/repo_final100_scale.csv
```

실행하면서 스크립트 밖에서 한 일 둘 (계산·기준은 그대로다):

- 한도 대기 상한(`max_wait_seconds`)을 900초에서 3,900초로 늘려 불렀다. 500개 평가는 한도(5,000회/시간)를 두 번 넘기는데, 기본 상한이면 남은 저장소가 `API_ERROR`로 끝난다
- 연결 끊김(`http.client.RemoteDisconnected`)을 `URLError`로 바꿔 스크립트의 기존 재시도에 태웠다. 스크립트는 `URLError`만 재시도해서 첫 실행이 201번째 저장소에서 죽었다 (§8 ⑥)
- **오래된 캐시를 치우고 다시 돌렸다.** 이유는 §9 ①에 있다. 다시 돌리는 사람은 `DATA_DIR/github_cache`에 2026-10-13 이전 응답이 남아 있으면 숫자가 달라진다

호출 수: 1단계 3,408회(첫 실행 3,211 + 캐시 정리 후 197), 2단계 5,481회(5,108 + 373).

### 1.3 기준별 적용

지시받은 기준과 스크립트에서의 위치, 결과다. **새로 만든 기준은 없다.**

| 기준 | 근거 | 적용 방법 | 결과 (1단계 502개 중) |
|---|---|---|---|
| Python 주 언어 | §4.3 ① | 검색 쿼리 `language:Python` (GitHub가 판정한 주 언어) | 전부 통과 |
| MIT / Apache-2.0 / BSD | §4.3 ②, ADR-007 | GitHub API `license.spdx_id`가 `PERMISSIVE_SPDX`에 있어야 함 (§3) | 제외 168 |
| 커밋 ≥ 1,000 | §4.3 ⑤ | 기본 브랜치 커밋 수 | 제외 137 |
| (최근 1년 커밋 있음) | 스크립트 기존 동작 | 표본을 뽑을 커밋이 없으면 제외 | 제외 9 |
| PR 경유 ≥ 70% (봇 제외) | §4.3 ③ | 최근 1년 사람 커밋 표본 30건 중 머지된 PR에 속한 비율. **컷으로 적용** | 후보 188개 중 통과 155 / 미달 33 |
| 이슈 참조 | §4.3 ④ | 컷이 아니다. 점수의 0.3 | — |
| 2015년 이후 시작 우선 | 선정 기준 v2 (#56) | **v2 그대로다.** 2015년 이전 시작은 제외하지 않고 `recent_only`로 채굴 구간만 2015년부터로 좁힌다. `score_v2`가 PR 비율·규모에 그 구간 값을 쓴다. 그 밖의 가산점·우선 규칙은 넣지 않았다 (§8 ②) | `recent_only` 19개 |
| 순위 | #56 | `score_v2 = 0.5·PR(채굴 구간) + 0.3·이슈 참조 + 0.2·규모(구간 커밋)` 내림차순 | 상위 80 |

- **PR 게이트를 컷으로 쓴 것은 이번이 처음이다.** `repo_selection.md` §5 ①은 하드 컷 여부를 "저장소를 늘릴 때 정한다"로 미뤘다. 이번 선정 지시가 "PR 경유 비율 ≥ 70%"를 기준으로 명시해 컷으로 적용했다. 게이트는 §4.3 ③대로 **최근 1년 값**(`pr_ratio`)에 건다. 채굴 구간 값(`window_pr_ratio`)에는 걸지 않았다 — v2에 그런 규칙이 없고, 확정 20개 중에도 0.70 미만이 넷 있다 (§2.3)
- 저장소별 회수율(`reports/labels_main500.md` §1.3)은 **선정에 쓰지 않았다.** 결과를 보고 고르는 것이 되기 때문이다. §2.1 표에 참고로만 옮겼다

### 1.4 기준 밖에서 한 판단 — `repo_final20.md` §2의 선례

§4.3에 없는 판단이 셋 들어갔다. 앞의 둘은 20개를 고를 때 사람이 한 판단을 그대로 따른 것이고, 셋째는 이번에 팀이 정했다 (2026-10-13, PR #172). 새 기준을 만든 것이 아니지만, **기준에 없는 제외라는 사실은 같다.** 팀이 되돌리려면 §4.3의 표에서 고르면 된다.

- **신생 저장소.** `repo_final20.md` §2.1은 첫 커밋 후 18개월이 안 된 저장소 4개를 뺐다. 같은 선(2026-10-13 기준 첫 커밋이 2025-04-13 이후)을 적용했다. 그때 뺀 4개는 날짜와 무관하게 그대로 뺐다 — `bytedance/deer-flow`(첫 커밋 2025-04-07)는 오늘 기준으로는 18개월을 6일 넘겼지만 이미 사람이 내린 결정이라 뒤집지 않았다
- **예제·목록 모음.** §2.2가 이름을 적어 둔 `TheAlgorithms/Python`·`public-apis/public-apis`·`Shubhamsaboo/awesome-llm-apps`를 뺐다. 같은 유형으로 본 `geekcomputers/Python`("My Python Examples")·`keon/algorithms`("Minimal examples of data structures and algorithms")도 뺐다. **이 둘은 Claude가 저장소 설명만 보고 한 판단이다. 사람이 확인해야 한다** (자동 규칙은 #25)
- **생성 코드 위주 저장소 — `ccxt/ccxt`.** TypeScript 원본에서 Python 등 다른 언어로 트랜스파일한 산출물이 대부분이다. 생성 코드를 거르는 `NOISE_GENERATED`가 미구현이라(`filter_rules.md`) 지금 필터로는 그 삭제가 그대로 통과한다. 크기도 단독으로 클론 약 10.7GB — 넣었을 때 신규 80개 클론 합계(44.9GB)의 24%였다. 기준(§4.3)은 모두 통과했고 `score_v2` 0.5800으로 신규 70위였다. 빈 자리는 81번째였던 `confident-ai/deepeval`(0.5196)로 채웠다. 근거로 쓴 측정값: 바이트 기준 Python 23%(TypeScript·C#·PHP·Go가 비슷하게 있다), 표본에서 변경 파일 50개 이상인 커밋이 변경 줄의 95%, 순회 커밋 약 8.6만, 채굴 구간 PR 연결 0.540. **"생성 코드가 대부분"이라는 판단 자체는 저장소 구조에 대한 팀의 판단이고, 생성 파일 비율을 재지는 않았다.** 같은 유형의 저장소가 100개 안에 더 있는지도 보지 않았다 (§8 ⑤)

이 판단으로 빠진 30개 중 26개는 점수로는 80개 안에 들었다 (§4.3 표의 "넣었다면 신규 순위").

## 2. 목록

값은 전부 2026-10-13 실행의 것이다. `PR 경유`는 최근 1년 표본, `PR 연결`은 연도별 표본 5건씩(채굴 구간)이고 괄호 안이 표본 수다.
`구간 커밋`은 채굴 구간의 기본 브랜치 커밋 수(병합 포함)다. 비고의 **XL**·**L**은 표시용 규모 구분이다 (§5.1).

## 3. 라이선스 확인 방법

- **자동 (99개).** GitHub REST `GET /repos/{owner}/{name}`의 `license.spdx_id`를 읽어 `select_repos.PERMISSIVE_SPDX`(MIT, MIT-0, Apache-2.0, BSD-2-Clause, BSD-3-Clause, BSD-3-Clause-Clear, BSD-4-Clause, 0BSD)에 있을 때만 통과시켰다. GitHub의 라이선스 탐지기(licensee)가 저장소 루트의 라이선스 파일을 보고 낸 값이다. CSV `license` 열이 이 값이다
- **수동 (1개).** `celery/celery`는 GitHub가 `NOASSERTION`을 준다. `repo_final20.md` §3.1에서 사람이 `LICENSE`를 읽어 BSD-3-Clause로 확인한 값을 `--license-override`로 넣었다 (CSV `license_manual=true`). 이번에 새로 수동 확인한 저장소는 없다
- **확인하지 않은 것.**
  - 자동 99개의 `LICENSE` 파일을 사람이 읽지 않았다. 탐지기가 맞다고 가정했다. 데이터셋 내보내기(#83) 전에 100개 전부 한 번은 사람이 봐야 한다 (#26~#28)
  - 하위 디렉터리에 다른 라이선스가 섞인 경우(celery `docs/`의 CC BY-SA처럼)는 이 방법으로 보이지 않는다
  - `NOASSERTION` 72개와 라이선스 정보가 없는 31개는 그대로 제외했다. celery처럼 사람이 확인하면 되살아날 저장소가 있을 수 있다 (§4.1)

### 5.1 지표와 한계

| 열 | 뜻 | 정확도 |
|---|---|---|
| 서버 크기 | GitHub API `size` | 정확한 값이지만 클론 크기가 아니다 |
| 클론 어림 | 서버 크기 × 1.3 | **어림.** 이 노트북에 남아 있는 클론 10개(9월에 받음)의 실제 크기 ÷ 서버 크기가 1.0~2.2(중앙값 1.3)였다. 2.2는 openpilot이다 — 클론은 6.5GB인데 서버 크기가 9월 6.4GB에서 지금 2.9GB로 바뀌었다 (원인은 확인하지 않았다). 나머지 9개는 1.0~1.5다 |

## 6. 맥락 결합 API 부담 (어림)

맥락 결합(`pipeline/context.py`)은 FULL_FUNCTION 레코드가 나온 커밋마다 GitHub API를 부른다 (#142). 커밋 하나에 드는 호출은 대략 다음과 같다.

- 커밋 → PR 조회 1회 (`/commits/{sha}/pulls`)
- PR이 있으면 리뷰 코멘트 1~2회 (`/pulls/{n}/comments`)
- 이슈 참조가 있으면 이슈 1~5회 (`/issues/{n}`)

같은 PR·이슈는 캐시가 받는다. FULL_FUNCTION 커밋이 몇 개 나올지는 추출 전에는 알 수 없다. 그래서 다음 식으로 어림했다.

```
API 호출 ≈ 순회 커밋 × (FULL_FUNCTION 커밋 비율) × (1 + PR 연결 비율 + issue_ref_ratio)
```

- **FULL_FUNCTION 커밋 비율**은 20개 실측에서 3.2%~12.6%, 중앙값 7.5%였다 (§5.2 표의 "비율"). 이 세 값으로 저·중·고를 낸다. 저와 고가 4배 차이다
- **검증.** 20개의 실제 호출 수는 기록이 남아 있지 않다. 대신 맥락 결과에서 `FULL_FUNCTION 커밋 수 + 서로 다른 PR 수 + 풀린 이슈 수`를 세어 대용값으로 삼았다 (실패한 조회·둘째 페이지는 빠지므로 실제보다 조금 작다). 참고로 pydantic의 대용값 1,087은 #82 코멘트의 실측 782회보다 크다 — 그때는 선정 스크립트가 남긴 캐시가 일부를 받았다
  - 어림(중) ÷ 대용값은 0.59~2.41배, 중앙값 1.10배였다. 저~고 범위 안에 대용값이 들어온 저장소는 20개 중 17개다
  - **저장소 하나의 어림은 2배쯤 틀릴 수 있다.** 합계와 분할의 균형을 보는 용도다
- **맥락 결합 개선(#128, #170)이 끝나면 호출 수 자체가 달라질 수 있다.** 이 어림은 지금 `context.py`의 동작 기준이다

| | PR 연결 커밋 (어림) | API 호출 저 | 중 | 고 | 토큰 1개로 (중) |
|---|---:|---:|---:|---:|---:|
| 신규 80 | 545,402 | 46,268 | **108,443** | 182,183 | 21.7시간 |
| 기존 20 (다시 돌린다면) | 300,615 | 25,094 | 58,813 | 98,804 | 11.8시간 |

"PR 연결 커밋"은 채굴 구간 전체의 값이다. FULL_FUNCTION 커밋만의 값이 아니다. 맥락 결합이 모든 커밋으로 넓어질 때의 상한으로 읽으면 된다.

## 9. 한계와 확인하지 않은 것

**① 9월 캐시가 섞여 있었다 — `repo_final20.md` §7.3의 원인이 이것으로 보인다.**
`select_repos.py`는 응답을 영구 캐시한다. 9월 10일에 평가한 106개는 "총 커밋 수" 응답이 그때 값으로 남아 있었다. 스크립트는 최초 커밋을 "커밋 목록의 마지막 페이지(= 총 커밋 수번째)"로 찾기 때문에, 커밋 수가 옛 값이면 그사이 쌓인 커밋 수만큼 덜 내려간 자리를 읽는다. 첫 실행에서 hermes-agent의 최초 커밋이 2026-07-27로 나와 알았다 (실제 2025-07-23).
- 조치: 2026-10-13 이전에 받은 저장소 정보·커밋 목록·검색 응답 478개를 캐시에서 빼고 1·2단계를 다시 돌렸다. PR·이슈 응답 캐시는 그대로 뒀다 (`context.py`가 쓴다)
- **9월 15일의 v2 재평가도 같은 일을 겪었다.** 그때는 9월 10일 커밋 수로 9월 15일의 목록을 읽었다. `repo_final20.md` §7.3이 "최초 커밋이 §1의 생성 연월보다 늦은 저장소가 8개다, 원인은 확인하지 않았다"고 적은 그 8개가 이번에는 전부 생성 연월과 맞는다 (vllm 2023-02-09, superset 2015-07-02, home-assistant 2013-09-17, transformers 2018-10-29, unsloth 2023-11-29, openpilot 2016-11-30, browser-use 2024-10-31, crewAI 2023-10-27)
- 영향: `recent_only` 판정은 20개 모두 그대로다 (2015년 경계를 넘은 저장소가 없다). unsloth·openpilot은 연도별 표본의 시작 연도가 한 해 앞당겨져 채굴 구간 PR 연결이 조금 내려갔다 (0.333 → 0.250, 0.300 → 0.273). **`repo_final20.md`·`repo_final20_v2.csv`는 고치지 않았다** (이번 범위 밖). 고칠지 정해야 한다

**② 검색 범위 500은 정한 값이다.** 상위 500개에서 게이트 통과 155개가 나와 80개를 채우기에 충분해서 멈췄다. 1,000개로 넓히면 더 높은 점수의 저장소가 들어와 70위 아래가 바뀔 수 있다. 검색 500번째의 별 수는 약 1.8만 개다.

**③ 판단 제외의 일부는 Claude가 했다.** `geekcomputers/Python`·`keon/algorithms`를 예제 모음으로 본 것, 그리고 신규 80개 중에 예제·목록 모음이 **없다**고 본 것 모두 저장소 설명과 토픽만 보고 한 판단이다. 저장소를 열어 보지 않았다. 사람이 80개를 한 번 훑어야 한다. 눈에 띈 경계 사례: `recommenders-team/recommenders`("Best Practices on Recommendation Systems" — 라이브러리와 예제 노트북이 같이 있다), `ungoogled-software/ungoogled-chromium`(Python 97%지만 패치·빌드 스크립트 저장소다), `nginx-proxy/nginx-proxy`(서버 크기 1MB, Python은 테스트 코드 위주로 보인다), `hummingbot/hummingbot`(거래소 커넥터가 대량으로 추가·삭제된다 — home-assistant의 통합 모듈과 같은 편중 우려, `repo_final20.md` §5 ⑨).
