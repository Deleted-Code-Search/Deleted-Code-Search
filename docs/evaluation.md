## 게이트 1 측정 방법 (라벨링 전 사전 확정, #37)

### 왜 지금 정하나

라벨링이 시작되기 전에 측정 코드가 커밋되어 있어야 한다. 라벨 결과를 보고 나서 임계값이나 집계 방식을
정하면 "60%가 나오도록 맞춘 것 아니냐"에 방어할 수 없다. 커밋 날짜가 그 증거다.

그래서 판정에 쓰는 숫자는 `eval/gate1.py` 상단 상수 한 곳에만 있고, 각 상수 위에 출처(§)가 주석으로 달려 있다.
`tests/test_gate1.py` 가 그 값(0.5 / 0.8 / 60% / 40% / 0.6)을 고정한다. **바꾸려면** 게이트 회의에서 결정하고,
그 커밋 본문에 결정과 근거를 적는다. 리포트(JSON)에는 측정에 쓴 상수가 함께 기록되므로, 어느 기준으로 잰
숫자인지 나중에도 확인할 수 있다.

### 입력과 실행

라벨러가 채우는 파일은 라벨 가이드 §7.2 개인 라벨(`datasets/labels/{labeler}_pre200.jsonl`)이다.
`tools/label_cli.py` 로 채운다 (README "라벨링").

```bash
python -m eval.gate1 datasets/labels/sj_pre200.jsonl datasets/labels/jh_pre200.jsonl \
    datasets/labels/hs_pre200.jsonl --json-out gate1.json --md-out gate1.md
python -m eval.gate1 datasets/labeled_500.jsonl      # 토론 확정(final)이 들어간 병합 파일
```

- 병합·등급 확정·쌍별 kappa 는 #34 `classify/labels.py` 를 그대로 쓴다. 같은 계산을 두 곳에 두지 않는다
- 8종·3등급 밖의 값, INFERRED 인데 신뢰도 없음, UNK 와 UNKNOWN 불일치, 같은 사람의 같은 레코드 중복이
  있으면 **숫자를 내지 않고 멈춘다** (파일:줄 번호 보고). 틀린 숫자로 게이트를 판정하느니 멈추는 편이 낫다

### 3구간 보고 규칙

**회수율은 단일 숫자로 보고하지 않는다.** INFERRED 를 어디까지 믿느냐에 따라 숫자가 움직이는데,
하나만 내면 그 민감도가 보이지 않는다.

| 구간 | 분자 | 경계 |
|---|---|---|
| ① EXPLICIT만 | EXPLICIT | — |
| ② EXPLICIT + INFERRED(≥ 0.5) | EXPLICIT + 신뢰도 **0.5 이상** INFERRED | 정확히 0.5 는 **포함** |
| ③ EXPLICIT + INFERRED(≥ 0.8) | EXPLICIT + 신뢰도 **0.8 이상** INFERRED | 정확히 0.8 은 **포함** |

- **분모는 세 구간 모두 같다:** 근거 등급이 확정된 레코드 수. 확정 = 토론 확정(`final`)이 있거나 2인의 등급이 일치.
  2인 등급이 갈렸거나 1인만 라벨한 건은 분모에서 빼고 건수를 따로 보고한다 (#34 와 같은 규칙).
  한쪽을 골라 세면 회수율이 토론보다 먼저 정해진다
- **INFERRED 의 신뢰도:** 토론 확정(DISCUSSED·THIRD_PARTY)이면 그 값, 아니면 **2인 중 작은 값** `[팀 확정 필요]`
- 가이드 §6.2 는 0.5 미만 INFERRED 를 금지하므로, 규칙을 지킨 라벨에서 **②가 CHARTER §15 정의 그대로의 회수율**이다.
  0.5 미만 INFERRED 가 있으면 어느 구간에도 세지 않고 경고로 건수를 낸다
- 저장소별 3구간도 함께 낸다 (§10.5, `docs/repo_final20.md` 재평가용). 건수가 적은 저장소는 신뢰구간이 넓다

### 판정 기준 (CHARTER §9 2주차)

| 회수율 | 판정 | 경계 |
|---|---|---|
| ≥ 60% | 진행 | 정확히 60% → **진행** |
| ≥ 40%, < 60% | 저장소 기준 강화 | 정확히 40% → **저장소 기준 강화** |
| < 40% | 대체 코드 중심으로 축 이동 | |

- 각 구간에 위 기준을 따로 적용한다. **세 구간 판정이 모두 같을 때만 그 판정이 확정**이고,
  하나라도 다르면 `판정 갈림 — 회의 필요`를 출력한다. 판정은 게이트 회의(`docs/meetings/gate-1.md`)에서 사람이 정한다
  `[팀 확정 필요]` (CHARTER §9 는 기준을 하나로만 적었다. 구간이 갈릴 때의 처리는 #37 에서 조장이 정한 규칙)
- 비율은 분수로 비교한다. 120/200 같은 값이 부동소수 오차로 경계 아래로 떨어지지 않는다

### 라벨 일치도 (게이트 1 과 함께 보고)

- Cohen's kappa 는 **2인이 모두 라벨한 건만**, 라벨러 쌍별로 따로 (가이드 §8.4). `anchored` 태그 건은 제외
- `reason_label`(8클래스)과 `evidence_grade`(3클래스)를 각각. p_o·p_e·혼동 쌍 상위 3개를 함께 낸다
- **kappa < 0.6 이면 CHARTER §11 라벨 품질 리스크 경고:** 라벨 가이드 개정(§5 보강), 애매 클래스 병합 검토
  (DESIGN/FEAT 등, 병합은 §13 절차). 정확히 0.6 은 경고하지 않는다
- 이유·등급 분포와 이유 × 등급 교차표를 개별 라벨 기준, 확정 레코드 기준으로 각각 낸다

**7. 표본 읽기 결과 (사전 탐색, 정식 측정 아님)**

PR이 연결된 FULL_FUNCTION 레코드를 저장소별로 10건씩 사람이 읽고, 이유를 판별할 수 있는지 판단했다.
표본 파일의 형식은 커밋 메시지 + PR 제목 + PR 본문 앞 500자다.

| 저장소 | 판별 가능 / 표본 | 비율 |
|---|---:|---:|
| psf/requests | 3 / 10 | 약 30% |
| encode/httpx | 6 / 10 | 약 60% |

- **판정자 1인, 표본 10건이므로 게이트 1 판정으로 쓰지 않는다**
- 표본 조건이 두 저장소에서 다르다. psf/requests는 구간별 4·3·3건이고 대량 커밋을 제외하지 않았다
  (1건이 레코드 477건짜리 커밋 2a6f290에서 나왔다). encode/httpx는 레코드 100건 초과 커밋(e27d1b8, 119건)을 제외했다.
  둘 다 커밋당 1건이다

**관찰.** psf/requests는 2011년 시작으로 초기 구간에 PR이 없고, PR이 있어도 릴리스 노트나 대규모 리팩터링이라
개별 함수의 삭제 이유가 없는 경우가 많았다. FULL_FUNCTION은 2011-2017에 집중되어, 데이터가 많은 구간과
이유가 기록된 구간이 어긋난다. encode/httpx는 2019년 시작으로 PR 본문에 삭제 함수명이 직접 언급되는 사례가 있었다.
§4.3의 PR 문화 기준은 최근 1년만 보므로(`docs/repo_selection.md` §2 "최근 1년 커밋 표본 30건") 이 차이를 걸러내지 못한다.
